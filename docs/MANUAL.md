# ns3-editor 使い方ガイド

ns-3 のシナリオをブラウザで組み立て、C++ コードを生成して実行するための GUI エディタ。
セットアップ・起動方法は [README](../README.md) を参照。ここでは画面の使い方を説明する。

## 画面構成

```
┌─────────────────────────────────────────────────────────┐
│ ns3-editor  [シナリオ名]  [保存] [読込▾] [検証]           │  ← ツールバー
├──────────┬──────────────────────────────┬────────────────┤
│          │                              │                │
│ パレット │           キャンバス          │  プロパティ    │
│          │                              │                │
├──────────┴──────────────────────────────┴────────────────┤
│ [シナリオ設定] [生成コード] [実行] [RPL テーブル]          │  ← 下部タブ
└─────────────────────────────────────────────────────────┘
```

- **パレット** (左): ノード・セグメントの追加ボタン
- **キャンバス** (中央): トポロジーを配置する場所。座標がそのまま `ConstantPositionMobilityModel` の位置 (px × スケール = メートル) になる
- **プロパティ** (右): 選択した要素 (ノード / セグメント) の設定
- **下部タブ**: シミュレーション全体の設定、生成コードのプレビュー、実行とログ、RPL の状態テーブル

## トポロジーを組み立てる

### ノードとセグメントの追加

パレットの「+ ノード」でノードを追加、「+ CSMA」「+ WiFi アドホック」「+ WiFi インフラ (AP)」「+ LR-WPAN (6LoWPAN)」で共有セグメントを追加する。

**セグメントへの参加は自動**: セグメントを追加すると、まだどの共有セグメントにも属していないノードを全部そのセグメントに参加させる。以降ノードを追加したときも、共有セグメントが 1 つしかなければ自動でそこに参加する (どちらに参加すべきか曖昧にならないケースだけ)。P2P リンクはセグメントではないので、これには影響しない。

複数のセグメント (複数の PAN、有線+無線の混在など) を作りたい場合は、2 つ目以降のセグメントは空で作られる。ノードをそこに参加させたい場合はノードの右クリックメニューから行う。

### 参加先の変更・PHY/MAC 設定 (右クリック)

ノードを右クリックすると:

- 参加ネットワーク一覧 — チェックボックスでセグメントへの参加/離脱を切り替え
- 参加中の各セグメントの「PHY/MAC 設定...」— プロパティパネルにジャンプ
- ノードを削除

セグメントを右クリックすると:

- PHY/MAC 設定を開く
- 全ノードをこのセグメントに参加させる
- セグメントを削除

参加/離脱はプロパティパネルの「メンバー」欄からも操作できる (外すボタン)。

### P2P リンク

ノードの下のハンドルから別のノードへドラッグすると P2P リンクになる。セグメントとは別物で、キャンバス上に線として描画される。

### セグメントの見え方

セグメントへの参加は、ハブへのスポーク線ではなく、ノード下のバッジ (セグメント ID) として表示される。ノード数が増えても線が放射状に増えないので見やすい。俯瞰図 (右下の MiniMap) にもトポロジーが色分け表示される (緑 = ノード、ベージュ = セグメント)。

### PHY/MAC パラメータ (セグメント単位)

セグメントを選択するとプロパティパネルに種別ごとの設定が出る:

| 種別 | 設定項目 |
|---|---|
| P2P | DataRate, Delay |
| CSMA | DataRate, Delay |
| WiFi (アドホック/インフラ) | 規格 (802.11a/b/g/n/ac/ax), SSID, (インフラのみ) AP ノード |
| LR-WPAN (6LoWPAN) | PAN ID, 伝搬損失モデル (LogDistance/Friis), エラーモデル (自動/常に有効/無効) |

WiFi はデフォルト設定だと約 50m を超えると受信できない (preamble 検出閾値 -82dBm)。ノード間隔に注意。

LR-WPAN のエラーモデルを「自動」にすると、RPL が MRHOF (ETX ベース) を使うときだけ有効になる。LQI が変動しないと ETX がホップ数と区別つかなくなるための措置 (ns-3 側の `contrib/rpl/examples/rpl-6lowpan-simple.cc` と同じ考え方)。

**おおよその通信範囲**: LR-WPAN または WiFi (アドホック/インフラ) のセグメントを含むシナリオでは、キャンバス右上に「通信範囲を表示 (LR-WPAN / WiFi)」というチェックボックスが出る。オンにすると、そのセグメントに参加しているノードそれぞれに、受信可能な範囲を示す点線の縁が重ねて表示される (見た目だけの補助線で、シミュレーションの挙動には影響しない)。半径は ns-3 の PHY の既定値から逆算した近似値:

- LR-WPAN: 送信電力 0 dBm・受信感度 -106.58 dBm。伝搬損失モデルは選んでいるものを使う (LogDistance: 既定の指数 3.0・基準損失 46.68 dB、Friis: 既定の周波数 5.15 GHz)
- WiFi: 送信電力 16.02 dBm・受信閾値 -82 dBm (preamble 検出、上の注記と同じ値)、伝搬損失モデルは常に LogDistance (既定値)。802.11 の規格を変えても、生成コードは送信電力を規格ごとに変えていないので円の大きさは変わらない

ノード間隔をこの縁の内側に収めれば互いに聞こえる、というノード配置の目安に使う。実際の受信可否は LR-WPAN ならエラーモデル (LQI)、WiFi なら SNR 由来の閾値の影響も受けるので、縁は目安であって厳密な境界ではない。トグルの状態は保存されない (シナリオ本体には含まれない表示設定)。

**LR-WPAN を追加すると IP スタックが自動で IPv6 に切り替わる** (6LoWPAN は IPv6 専用)。ルーティングが Global (IPv4 専用) だった場合は Static に変わる。RPL は明示的に選ぶ必要がある (下記)。

## シナリオ設定 (下部タブ)

### シミュレーション

- 時間 (s) / シード / スケール (px = m)
- pcap を書き出すか (実行後 `runs/<timestamp>/` に保存される)
- ログコンポーネント (カンマ区切り、`NS_LOG` に相当。例: `RplRoutingProtocol, Ping`)
- **RPL テーブル取得間隔 (s)**: ルーティングが RPL のときだけ表示。この間隔で各ノードの RPL 状態のスナップショットを取り、「RPL テーブル」タブで参照できるようにする。`0` にすると定期取得を止め、実行終了時の 1 回だけになる (実行ログ末尾の人間可読なダンプは間隔の設定によらず常に出る)

### スタック

- IP: IPv4 / IPv6
- ルーティング: Global (IPv4 専用) / Static / RPL (IPv6 専用)
- RPL を選ぶと instance ごとの設定リストが出る (「+ RPL instance」で追加、各行の「削除」で削除。最後の 1 件は削除不可):
  - **DODAG root**: 起点ノード。省略不可
  - **Objective Function**: OF0 (ホップ数) / MRHOF (ETX)
  - **LQL を advertise**: RSSI 由来のリンク品質を DIO に含めるか

  実際に ns-3 へ渡され動作するのは先頭 (instance 0, "base") のみ。2 つ目以降は
  将来 contrib/rpl 側が複数 RPL Instance の join に対応した際のための空の枠で、
  今追加しても生成コード・シミュレーションには影響しない。

  base instance の行には「RPL 詳細設定 (Trickle/DAO)」という折りたたみがある。
  RFC 6550 の core RPL パラメータで、contrib/rpl (`rpl::RplRoutingProtocol`)
  のデフォルト値と一致する値のままなら生成コードには一切現れない (値を変えた
  項目だけ `rplHelper.Set(...)` として出る):
  - **DIS 送信間隔 (s)**: DODAG 未参加時に撒く unsolicited DIS の周期 (既定 30s)
  - **DIO Trickle Imin / doublings**: DIO Trickle タイマーの最小間隔と、
    最大間隔 (Imax = Imin << doublings) までの倍化回数 (既定 4.096s / 8 =
    Imax 約17.5分)。root のみがこの値を使い、他ノードは join した DIO の
    DODAG Configuration オプションから引き継ぐ
  - **DIO Trickle redundancy k**: 0 で抑制なし (既定)。Trickle の一貫性カウント
    による送信抑制のしきい値
  - **MinHopRankIncrease**: root の rank でもある、1 ホップあたりの rank
    増分 (既定 128)
  - **DAO 再送間隔・DAO-ACK タイムアウト・DAO 再送回数**: 下り経路を root に
    伝える DAO の再送スケジュール (既定 60s / 5s / 3 回)
  - **下り経路の寿命 (lifetime units)**: DAO が広告する経路の寿命
    (既定 30 unit。1 unit = 60 秒固定、contrib/rpl 側で unit 自体は
    attribute 化されていない)

  base instance の行にはもう1つ「AODV-RPL 探索設定 (詳細)」という折りたたみも
  ある。下記の AODV-RPL 探索アプリが使う Trickle・RankLimit・寿命のパラメータで、
  探索アプリを 1 つも追加していないシナリオでは生成コードに一切現れない。

### アプリケーション

「+ Ping」「+ UDP Echo」「+ OnOff」で追加。追加された行で編集できるのは送信元/宛先ノードと開始時刻、Ping はそれに加えて回数。パケット間隔・サイズ・データレートなどそれ以外のパラメータは追加時のデフォルト値のままになる (Ping: 5 回・1 秒間隔。UDP Echo: 10 パケット・1 秒間隔・64 バイト・port 9。OnOff: 500kbps・512 バイト・port 9000)。細かく調整したい場合はシナリオ保存後、`scenarios/<name>.json` を直接編集して読み込み直す。

**RPL シナリオでの注意**: RPL ノードはアドレスを固定で持たず、シミュレーション実行中に SLAAC で決まる。生成コードはこれを踏まえて、DODAG が収束してから (宛先・送信元の両方がグローバルアドレスを持ち、root が全ノードの DAO を受け取るまで) アプリを起動するようスケジュールする。収束が遅いトポロジー (ノード数が多い、間隔が広い) では開始時刻を早く設定しすぎると、収束前にリトライを繰り返すだけで実際の送信が遅れる。逆に極端に収束が遅いと、収束したと判定された時点でも経路がまだ不安定でパケットが届かないことがある (クラッシュはしない)。開始時刻に余裕を持たせるのが安全。

**「+ AODV-RPL 探索」** (ルーティングが RPL のときだけ表示): RFC 9854
AODV-RPL の経路探索を起動する。起点ノード・ターゲットノード・開始時刻を
指定すると、生成コードは起点ノードで `RplRoutingProtocol::DiscoverRoute()`
を呼ぶ (両端が SLAAC アドレスを持つまで自己再スケジュールする点は他の
アプリと同じだが、こちらは base DODAG の収束 (root が全ノードの DAO を
受け取ること) を待たない — AODV-RPL は DAO の木とは独立に、自分専用の
RREQ-Instance を flood して経路を探すため)。見つかった経路は自動的に
以後の通信に使われる (`RouteOutput()`/`PrepareOutgoingPacket()` が
base DODAG の経路より先に AODV-RPL の経路を見る) ので、探索が終わる
だけの時刻より後の start を持つ別の Ping/OnOff アプリを同じ 2 ノード間に
足せば、見つかった経路に実際にトラフィックを流して確認できる。停止時刻の
概念は無い (1 回限りの呼び出し)。発見した経路は「RPL テーブル」タブには
まだ出ない (contrib/rpl 側の既知の制約) — ログコンポーネントに
`RplAodv` を足せば `NS_LOG` 経由で探索の様子を追える。

## 検証・生成・実行

1. **検証** (ツールバー): トポロジー・スタック・アプリの整合性をチェック。エラーがあると生成できない (メンバー不足、ID 重複、宛先ノードが存在しない、など)。警告は生成を妨げない (孤立ノードなど)
2. **生成コード** タブ: 検証を実行し、C++ プレビューを表示。ファイルは `<ns-3 リポジトリ>/scratch/ns3edit-<シナリオ名>.cc` に書かれる
3. **実行** タブ: 「実行」ボタンで `./ns3 run` を起動し、ログを WebSocket でライブ表示。「停止」で中断できる。完了後、pcap などの成果物がリンクとして表示される (`runs/<timestamp>/` に保存)

実行は同時に 1 本まで (ns-3 のビルドロック衝突を避けるため)。既に実行中に「実行」を押すとエラーになる。

## RPL テーブル (下部タブ)

ルーティングが RPL のシナリオで、各ノードが実際にどんな状態になっているかを実行中・実行後に参照できる。

- **時刻スライダー**: 取得済みスナップショットの時刻を選ぶ。触っていない間は最新に追従するので、実行中はそのまま眺めていれば収束していく様子が見える。過去に遡ったあと最新に戻すには「最新へ」ボタン
- **ノード選択**: 表示するノードを選ぶ

選択したノードについて表示されるもの:

- rank、preferred parent、DODAGID、使用中の Objective Function、path ETX、DODAG version
- **候補親テーブル**: アドレス / rank / インターフェース / 受信回数 (freshness) / 最終受信からの経過 / link ETX / path ETX / LQL。現在の preferred parent の行は強調表示される
- **root のトポロジ**: root が DAO から組み立てた「どのノードがどの親の下にいるか」の表。ターゲット / 親 / path sequence / 残り寿命。非 root ノードを選んでいるときも root のぶんは併せて表示される (non-storing mode で下り経路を知っているのは root だけなので)

値が `-` になっているのは、その設定では意味を持たない項目 (OF0 のときの link/path ETX、LQL を advertise していないときの LQL)。残り寿命の「無期限」は、その経路が Path Lifetime 0xFF (RFC 6550 6.7.8 節の無限) で広告されたことを意味する。

データは生成コードが標準出力に出す 1 行 1 JSON のスナップショットで、バックエンドがそれを実行ログから抜き出して WebSocket で配信している。そのため実行ログ側には JSON は現れない。

## 保存・読込

ツールバーの「保存」でシナリオ名を使って `scenarios/<name>.json` に保存、「読込」プルダウンから既存シナリオを開く。

同梱サンプル:

- `wifi-adhoc-ping` — IPv4 WiFi アドホック 2 ノード、Ping
- `rpl-line` — LR-WPAN 3 ノード直列、RPL MRHOF+LQL、Ping
- `rpl-mesh` — LR-WPAN 5 ノードのメッシュ (隣接 50m、LR-WPAN の到達範囲内)、RPL MRHOF+LQL、Ping。DODAG がきちんと収束する配置の実例
- `rpl-aodv-mesh` — `rpl-mesh` と同じ配置、AODV-RPL 探索 ("b" から "c" へ)。base DODAG の木では root 経由の 4 ホップになる 2 ノード間が、AODV-RPL では直接 1 ホップの経路として見つかる実例 (`./ns3 run` で実際に確認済み)

## 生成コードを直接触りたいとき

生成された `scratch/ns3edit-<name>.cc` の先頭には「エディタから再生成される、直接編集しないこと」という注記がある。ns-3 側だけで確認したい場合:

```bash
./ns3 build ns3edit-<name>
./ns3 run ns3edit-<name>
```

## 既知の制約

- **RPL 収束待ちは近似的**: root のトポロジーサイズ (DAO を受け取ったノード数) が全ノード分揃ったことをもって「収束した」と判定する。これは経路の実際の安定性までは保証しないため、収束直後に送ったパケットが届かないことがある (再送やアプリの継続実行で回収されることが多い)
- **PHY/MAC はセグメント単位**: ns-3 のヘルパーがデバイス群に一括設定する構造をそのまま反映しており、ノードごとに異なる PHY/MAC を持たせることはできない
- **LR-WPAN の距離**: `wifi` ほど厳密なプリセットの目安がない。`rpl-mesh` サンプル (隣接 50m) を基準にするとよい
- **AODV-RPL 経路は「RPL テーブル」タブに出ない**: `PrintRoutingTableJson()` (contrib/rpl 側) が今のところ base DODAG のトポロジーしか出さないため。探索の成否は生成コードの実行ログか、`RplAodv` ログコンポーネントで確認する
