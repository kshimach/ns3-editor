# ns3-editor 使い方ガイド

ns-3 のシナリオをブラウザで組み立て、C++ コードを生成して実行するための GUI エディタ。
セットアップ・起動方法は [README](../README.md) を参照。ここでは画面の使い方を説明する。

## 画面構成

```
┌──────────────────────────────────────────────────────────────────┐
│ ns3-editor [名前●][新規▾][開く▾][保存] │ ↶↷ │ ✕1⚠2 │ [▶ 実行]      │  ← ツールバー
├──────────┬──────────────────────────────┬────────────────────────┤
│          │                              │  [要素][設定][RPL]      │
│ パレット │           キャンバス          │                        │  ← 右パネル
│          │  (右上に表示トグル・?ボタン)  │  選択中の要素 /         │    (ドラッグでリサイズ)
│          │                              │  シミュレーション・     │
│          │                              │  スタック・アプリ /     │
│          │                              │  RPL 詳細パラメータ     │
├──────────┴──────────────────────────────┴────────────────────────┤
│ [問題][コード][実行ログ][RPL テーブル]                       ▼    │  ← 下部パネル
└─────────────────────────────────────────────────────────────────┘    (ドラッグでリサイズ・折りたたみ可)
```

- **パレット** (左): ノード・セグメントの追加ボタン
- **キャンバス** (中央): トポロジーを配置する場所。座標がそのまま `ConstantPositionMobilityModel` の位置 (px x スケール = メートル) になる。空の状態では操作手順とサンプル一覧が表示される
- **右パネル**: 「要素」(選択中のノード/セグメントの設定)・「設定」(シミュレーション・スタック・アプリ)・「RPL」(RPL の全パラメータ) の3タブ
- **下部パネル**: 「問題」(検証結果)・「コード」(生成コードのプレビュー)・「実行ログ」・「RPL テーブル」の4タブ。ヘッダをクリックで折りたたみ可能
- 右パネルと下部パネルの境界はドラッグで幅・高さを変更でき、次回起動時も保持される

## トポロジーを組み立てる

### ノードとセグメントの追加

パレットの「+ ノード」でノードを追加、「+ CSMA」「+ WiFi アドホック」「+ WiFi インフラ (AP)」「+ LR-WPAN (6LoWPAN)」で共有セグメントを追加する。**キャンバスを右クリックしても同じメニューが出る**(その位置に追加される)。

**セグメントへの参加は自動**: セグメントを追加すると、まだどの共有セグメントにも属していないノードを全部そのセグメントに参加させる。以降ノードを追加したときも、共有セグメントが 1 つしかなければ自動でそこに参加する。この自動参加や、LR-WPAN 追加時の IPv6 自動切り替えが起きると、画面下に短いトースト通知が出る。

複数のセグメント (複数の PAN、有線+無線の混在など) を作りたい場合は、2 つ目以降のセグメントは空で作られる。ノードをそこに参加させたい場合はノードの右クリックメニューか、右パネル「要素」タブの「所属ネットワーク」チェックボックスから行う。

### 参加先の変更・PHY/MAC 設定 (右クリック)

ノードを右クリックすると:

- 参加ネットワーク一覧 — チェックボックスでセグメントへの参加/離脱を切り替え
- 参加中の各セグメントの「PHY/MAC 設定...」— 右パネル「要素」タブへジャンプ
- RPL ルーティング時は「DODAG root にする」
- 「このノードからアプリを追加」— Ping/OnOff/(RPL 時のみ) AODV-RPL・P2P-RPL 探索をワンクリックで追加
- ノードを削除

セグメントを右クリックすると:

- PHY/MAC 設定を開く
- 全ノードをこのセグメントに参加させる
- セグメントを削除

参加/離脱は右パネル「要素」タブの「所属ネットワーク」からも操作できる。

### P2P リンク

ノードの下のハンドルから別のノードへドラッグすると P2P リンクになる。セグメントとは別物で、キャンバス上に線として描画される。両端はちょうど 2 ノード固定で、変更したい場合はリンクを削除してから別のノード間へ改めてドラッグする。

### セグメントの見え方

セグメントへの参加は、ハブへのスポーク線ではなく、ノード下のバッジ (セグメント ID) として表示される。ノード数が増えても線が放射状に増えないので見やすい。俯瞰図 (右下の MiniMap) にもトポロジーが色分け表示される (緑 = ノード、ベージュ = セグメント)。RPL の DODAG root には王冠アイコンが付く。

### PHY/MAC パラメータ (セグメント単位)

セグメントを選択すると右パネル「要素」タブに種別ごとの設定が出る:

| 種別 | 設定項目 |
|---|---|
| P2P | データレート (DataRate), 遅延 (Delay) |
| CSMA | データレート (DataRate), 遅延 (Delay) |
| WiFi (アドホック/インフラ) | 規格 (802.11a/b/g/n/ac/ax), SSID, (インフラのみ) AP ノード |
| LR-WPAN (6LoWPAN) | PAN ID, 伝搬損失モデル (LogDistance/Friis), エラーモデル (自動/常に有効/無効) |

WiFi はデフォルト設定だと約 50m を超えると受信できない (preamble 検出閾値 -82dBm)。ノード間隔に注意。

LR-WPAN のエラーモデルを「自動」にすると、RPL が MRHOF (ETX ベース) を使うときだけ有効になる。LQI が変動しないと ETX がホップ数と区別つかなくなるための措置。

**おおよその通信範囲**: キャンバス右上の「通信範囲を表示 (LR-WPAN / WiFi)」チェックボックスをオンにすると、該当セグメントに参加しているノードそれぞれに受信可能な範囲の点線が重ねて表示される (見た目だけの補助線)。同じ場所に「ノード ID を表示」(名前と ID を両方表示) と、RPL 実行後は「RPL 親リンクを重ねる」(各ノードから preferred parent への矢印を表示) のトグルも並ぶ。

**LR-WPAN を追加すると IP スタックが自動で IPv6 に切り替わる** (6LoWPAN は IPv6 専用)。ルーティングが Global (IPv4 専用) だった場合は Static に変わる。RPL は明示的に選ぶ必要がある (下記)。

## 右パネル「設定」タブ

### シミュレーション

- 時間 (s) / シード / スケール (px = m)
- pcap を書き出すか (実行後 `runs/<timestamp>/` に保存される)
- ログコンポーネント (カンマ区切り、`NS_LOG` に相当。例: `RplRoutingProtocol, Ping`)
- **RPL テーブル取得間隔 (s)**: ルーティングが RPL のときだけ表示。この間隔で各ノードの RPL 状態のスナップショットを取り、「RPL テーブル」タブで参照できるようにする。`0` にすると定期取得を止め、実行終了時の 1 回だけになる

### スタック

- IP: IPv4 / IPv6
- ルーティング: Global (IPv4 専用) / Static / RPL (IPv6 専用)
- RPL を選ぶと右パネルに「RPL」タブが有効になり、そちらで DODAG root などを設定する

### アプリケーション

右パネル下部の「+ アプリを追加...」から種類を選んで追加する。追加されたアプリは 1 枚のカードとして表示され、**そのアプリが持つ全パラメータを編集できる**:

| 種類 | 編集できる項目 |
|---|---|
| Ping | 送信元/宛先, 開始時刻, 終了時刻, 回数, 送信間隔 |
| UDP Echo | クライアント/サーバー, 開始/終了時刻, ポート, 最大パケット数, 送信間隔, パケットサイズ |
| OnOff | 送信元/宛先, 開始/終了時刻, ポート, データレート, パケットサイズ |
| AODV-RPL 探索 | 送信元/宛先, 開始時刻, H=1 (hop-by-hop) |
| P2P-RPL 探索 | 送信元/宛先, 開始時刻, H=1 (hop-by-hop) |

終了時刻は「指定する」チェックを外すと無期限 (アプリケーションを停止しない) になる。AODV-RPL/P2P-RPL 探索アプリは 1 回限りの呼び出しなので終了時刻の概念がない。

**RPL シナリオでの注意**: RPL ノードはアドレスを固定で持たず、シミュレーション実行中に SLAAC で決まる。生成コードはこれを踏まえて、DODAG が収束してから (宛先・送信元の両方がグローバルアドレスを持ち、root が全ノードの DAO を受け取るまで) アプリを起動するようスケジュールする。収束が遅いトポロジー (ノード数が多い、間隔が広い) では開始時刻を早く設定しすぎると、収束前にリトライを繰り返すだけで実際の送信が遅れる。開始時刻に余裕を持たせるのが安全。

**AODV-RPL / P2P-RPL 探索**: 起点ノード・ターゲットノード・開始時刻を指定すると、生成コードは起点ノードで `RplRoutingProtocol::DiscoverRoute()` / `DiscoverP2pRoute()` を呼ぶ。base DODAG の収束を待たず、自分専用の RREQ-Instance / 一時 DAG を flood して経路を探す。見つかった経路は自動的に以後の通信に使われるので、探索が終わるだけの時刻より後の start を持つ別の Ping/OnOff アプリを同じ 2 ノード間に足せば、見つかった経路に実際にトラフィックを流して確認できる。発見した経路は起点ノードの「RPL テーブル」タブに表示される。source routing (H=0) の場合は中継ノードやターゲット自身には何も残らず、その表は起点ノードでだけ埋まる。H=1 (hop-by-hop) にすると各中継ノードが次ホップだけを覚える。詳しい探索の様子を追いたければログコンポーネントに `RplAodv` / `RplP2p` を足せば `NS_LOG` 経由でも見られる。

## 右パネル「RPL」タブ

ルーティングが RPL のときだけ有効になる。base (instance 0) の設定のみを扱う。2 つ目以降の RPL instance は現状 ns-3 に渡されず未使用 (contrib/rpl の複数 instance 対応待ち) で、そのまま JSON に残るだけの表示専用の注記が出る。

- **DODAG root**: 起点ノード。省略不可 (キャンバスでのノード右クリックからも指定できる)
- **Objective Function**: OF0 (ホップ数) / MRHOF (ETX)
- **LQL を advertise**: RSSI 由来のリンク品質を DIO に含めるか
- **Mode of Operation**: Non-storing (下りは root だけが Source Route を保持) / Storing (各ルータが下り経路も保持)

各項目名の横の「?」アイコンにカーソルを合わせると説明が出る。既定値から変更した項目には「●」マークと「既定に戻す」ボタンが付く。

3 つの折りたたみに詳細パラメータがある (「RPL 詳細設定 (Trickle/DAO)」「AODV-RPL 探索設定 (詳細)」「P2P-RPL 探索設定 (詳細)」)。既定値のままの項目は生成コードに一切現れない。AODV-RPL / P2P-RPL の詳細は、対応する探索アプリを 1 つも追加していないシナリオでは生成コードに現れない。

## 下部パネル

### 問題

シナリオの検証結果 (エラー・警告) をリアルタイムに表示する。編集するたびに自動で再検証されるので、手動で「検証」を押す必要はない。行をクリックすると、対応するノード/セグメントがキャンバス上で選択され、対応するアプリの場合は右パネル「設定」の当該カードへ移動する。エラーが 1 件でもあると生成・実行はできない。ツールバーの `✕N ⚠N` バッジをクリックしてもこのタブが開く。

### コード

「コードを生成して表示」を押すと C++ プレビューが表示される。ファイルは `<ns-3 リポジトリ>/scratch/ns3edit-<シナリオ名>.cc` に書かれる。

### 実行ログ

ツールバーの「▶ 実行」を押すと `./ns3 run` が起動し、ログがここにライブ表示される (実行中はタブが自動でここに切り替わる)。同じ位置のボタンが「■ 停止」に変わり、押すと中断できる。完了後、pcap などの成果物がリンクとして表示される (`runs/<timestamp>/` に保存)。実行は同時に 1 本まで。

### RPL テーブル

ルーティングが RPL のシナリオで、各ノードが実際にどんな状態になっているかを実行中・実行後に参照できる。

- **時刻スライダー**: 取得済みスナップショットの時刻を選ぶ。触っていない間は最新に追従する
- **ノード選択**: 表示するノードを選ぶ。キャンバスでノードを選択すると自動でここも切り替わる (逆も同様)

選択したノードについて表示されるもの:

- rank、preferred parent、DODAGID、使用中の Objective Function、path ETX、DODAG version
- **候補親テーブル**: アドレス / rank / インターフェース / 受信回数 (freshness) / 最終受信からの経過 / link ETX / path ETX / LQL
- **下り経路 (Storing)**: Storing mode のときに各ノードが保持する下り経路 (ターゲット / 次ホップ / path seq / 残り寿命)
- **AODV-RPL 経路** / **P2P-RPL 経路**: 探索で見つかった経路
- **root のトポロジ**: root が DAO から組み立てた「どのノードがどの親の下にいるか」の表 (Non-storing の下り経路はここにのみ現れる)

**確認済みループ**: RankErrorConfirmed トレース (実際にパケットが通ってルーティングループが検出されたイベント) が 1 件でもあると、赤いバッジ付きの一覧がタブ上部に表示される。行にカーソルを合わせるとキャンバス上の該当ノードが赤くパルスし、クリックで選択・ジャンプする。

値が `-` になっているのは、その設定では意味を持たない項目。残り寿命の「無期限」は Path Lifetime 0xFF (無限) を意味する。

## 保存・読込・新規・元に戻す

- **新規▾**: 「空のシナリオ」または各サンプルから新規作成
- **開く▾**: サンプル / 保存済みシナリオ (削除ボタン付き) の 2 セクション
- **保存 (⌘S)**: 現在の名前で `scenarios/<name>.json` に保存
- 未保存の変更があるとシナリオ名の横に ● が表示され、破棄が伴う操作 (新規・読込・タブを閉じる) の前に確認を求める
- **↶ / ↷ (⌘Z / ⌘⇧Z)**: 直近の編集を取り消す/やり直す。まとまった一連の操作 (ドラッグ、連続入力) は 1 ステップにまとまる

同梱サンプル (「新規▾」「開く▾」から選べる):

- `wifi-adhoc-ping` — IPv4 WiFi アドホック 2 ノード、Ping
- `rpl-line` — LR-WPAN 3 ノード直列、RPL MRHOF+LQL、Ping
- `rpl-mesh` — LR-WPAN 5 ノードのメッシュ (隣接 50m、LR-WPAN の到達範囲内)、RPL MRHOF+LQL、Ping
- `rpl-aodv-mesh` — `rpl-mesh` と同じ配置、AODV-RPL 探索。base DODAG の木では root 経由の 4 ホップになる 2 ノード間が、直接 1 ホップの経路として見つかる実例
- `rpl-p2p-mesh` — `rpl-aodv-mesh` と全く同じ配置・同じ 2 ノード間を P2P-RPL で探索する版

## ヘルプ・キーボードショートカット

キャンバス右上の「?」ボタン (またはキーボードの `?`) で操作ガイドが開く。

| ショートカット | 動作 |
|---|---|
| Delete / Backspace | 選択中の要素を削除 |
| Escape | 選択解除・メニュー/モーダルを閉じる |
| ⌘S / Ctrl+S | 保存 |
| ⌘Z / Ctrl+Z | 元に戻す |
| ⌘⇧Z / Ctrl+Shift+Z | やり直す |
| ⌘Enter / Ctrl+Enter | 実行 |
| ? | ヘルプを開く |

## 生成コードを直接触りたいとき

生成された `scratch/ns3edit-<name>.cc` の先頭には「エディタから再生成される、直接編集しないこと」という注記がある。ns-3 側だけで確認したい場合:

```bash
./ns3 build ns3edit-<name>
./ns3 run ns3edit-<name>
```

## 既知の制約

- **RPL 収束待ちは近似的**: root のトポロジーサイズ (DAO を受け取ったノード数) が全ノード分揃ったことをもって「収束した」と判定する。これは経路の実際の安定性までは保証しないため、収束直後に送ったパケットが届かないことがある (再送やアプリの継続実行で回収されることが多い)
- **PHY/MAC はセグメント単位**: ns-3 のヘルパーがデバイス群に一括設定する構造をそのまま反映しており、ノードごとに異なる PHY/MAC を持たせることはできない
- **LR-WPAN の距離**: `wifi` ほど厳密なプリセットの目安がない。`rpl-mesh` サンプル (隣接 50m) を基準にするとよい
- **RPL instance は 1 つのみ有効**: 複数 instance の JSON を読み込んでも、ns-3 に渡され動作するのは先頭 (instance 0) だけ
